# M2 participant trials before exhaustive verification

This is the default M2 iteration order, approved by the owner on 2026-09-22:

**Repair → focused checks → frozen participant trial → feedback and repair;
after a successful stable trial → complete automated verification → closure.**

It replaces the blanket requirement to complete Gate8/bootstrap/release before
any participant exposure. It changes scheduling, not the carrier ceiling,
damage promises, independent implementations, final gates, participant tasks,
freshness, assistance, saved-method checkpoints or retry limits. This is an M2
development rule; the later M4/M5 final-evaluation barriers remain unchanged.
The roadmap remains the sole milestone-status authority.

## Before a trial

Use the cheapest checks that address the actual edit and the complete trial
package. All of the following are required before a provisional blind trial:

1. Run `scripts/check fast` and the affected direct/component regressions.
   Check the repaired teaching relationships, including relevant failure and
   conflict cases. Passing primitive examples alone does not establish complete
   damaged-group recovery.
2. Build the actual carrier from the current source. Check the 512 KiB ceiling,
   complete route/recipe/layout consistency, clean recovery and exact content.
   No manually patched carrier, miniature substituted for actual content, old
   decoder result or participant answer is a generation input.
3. Independently check Python/Rust agreement and the source oracle on the clean
   carrier and **every observation to be handed out**, including the existing
   A=D3/0, B=D2/0, C=D4/0 and D=D7/11 cases. Check expected failures as well as
   successes. Include affected boundary regressions; a sample is not a complete
   damage-corpus pass. The development `replay_damage_v2.py --selection preflight`
   is the bounded cross-language replay, not `--selection all`.
4. Freeze the source snapshot, exact recipient files, owner expected results,
   scoring/acceptance rules, allowed information and staged handoff before
   exposure. Preserve ordinary command logs and hashes in the ignored trial
   folder. No new form, database, service, consent step or participant task is
   required. If the existing preview tool does not prove a required check,
   complete that check separately; a preview manifest alone is insufficient.

Use the real source-built participant packagers and their existing separation
of recipient and owner files. Learner trials use the exact lesson stream
recovered by the technical trial, the generic runner and its existing twelve
finals. Package only the selected trial, not all damage cases. Keep outputs
outside canonical candidate/Gate8/report paths. Snapshot and package equality
are checked before handing them out and again when evaluating the result.

Do not run the full corpus, four production producers, full physical proof,
Gate8 assembly, clean Linux or composed release merely to enable a trial.
Run a larger diagnostic only when a concrete fault requires it, with that
reason in the existing work notes. Never turn a focused pass into a full gate
receipt, Candidate-ready report or completed milestone.

## Participant work and its meaning

Two uses are distinct, without different participant paperwork:

- **Formative:** a previous or helped participant can explore a repair and
  explain remaining confusion. Their work informs design and remains formative.
- **Provisional blind trial:** a fresh eligible person receives the frozen
  material in the normal order, without substantive hints. Before exposure,
  record that a successful result is pending complete automated verification.
  Preserve clean method → thin adapter → all held-outs/query → final account.
  A learner may follow a successful provisional technical trial using its exact
  recovered lesson bytes, without waiting for exhaustive verification.

Extra effort, repeated sessions, wrong starts and backtracking are welcome.
Later decoder changes remain useful diagnostics and cannot retroactively pass
the earlier saved-method checkpoint. Keep all failed/unresolved results visible;
the existing one-diagnosed-unchanged-retry limit still applies. A cosmetic change
or switching this workflow does not reset it. The reviewed 08/10 attempts remain
historical; this rule does not retroactively reclassify either as a pass.

A failed trial normally goes directly back to repair and focused checks. It
does not trigger an exhaustive run to discover that the same teaching needs
another change. A successful provisional result stays **pending**, not
qualifying, until the final requirements below are met. The participant need
not repeat a successful trial solely because automated checks run afterward.

## Final verification and reconciliation

Once the teaching and trial package are stable and the required provisional
technical and learner results succeed, run all existing final requirements:
the complete D0–D7 corpus and B0/boundary checks, resource bounds, independent
native and clean-Linux production, physical evidence, deterministic selection,
exact bundle/report assembly and composed release. No family, case, producer,
wrong-accept check or final threshold is removed or sampled away.

The final reviewer must compare the preserved trial with the final source and
generated bundles. Recipient bytes, staged information conditions, expected
answers and acceptance rules must match exactly. Source changes cannot be
ignored merely because a carrier hash matches. A change to the tested recovery
or learning contract, interpretation, scoring or expected result makes the
affected human evidence stale. A bounded nonsemantic implementation/test repair
may retain human evidence only with an explicit source diff and fresh checks
proving the relevant candidate, recipient files, expected outcomes and conditions
unchanged; rerun its affected automated checks. Unresolved equivalence rejects.

An automated failure prevents final acceptance even after a successful human
trial. Repair it; if it changes the trial's material or conditions, repeat the
affected human validation on the new frozen version. Never adjust a rubric to
rescue an observed answer, reuse stale receipts, or relabel formative/hinted work.

Only after this reconciliation and all final gates pass may a provisional blind
success become the qualifying result. Until then keep it in ordinary trial notes
with its files and hashes. The current automated Candidate-ready report schema
still contains pending human fields; this workflow does not invent a new report
enum or silently admit human summaries through the existing generator.

Run expensive commands at the final stable barrier. Do not run standalone
`full` and `linux` and then immediately `release` on the same frozen inputs;
`release` already composes those checks. Existing bootstrap/assembly/release
requirements remain where their commands require them. This change does not
claim those implementations now reuse work or eliminate their internal replays.
After a verified final snapshot, repeat expensive work only for an actual input
change, failed check or unresolved concern that invalidates it. Report measured
focused-check times; do not promise an unmeasured duration.
